# 版本目录、保密与交付合同

## 版本规则

每次首次生成或实质迭代使用新的时间戳版本目录。目录已包含时间戳时，内部文件使用稳定、可读名称，不再强制每个文件重复时间戳。

默认结构：

```text
<案件版本目录>/
├── 00-优化说明.md
├── 01-交付文件清单.md
├── 02-文件校验.sha256
├── 技术交底书/
│   ├── 技术交底书.docx
│   └── 技术交底书_正文.md
├── 申请文件/
│   ├── 题目.md
│   ├── 说明书摘要.md
│   ├── 权利要求书.md
│   ├── 说明书.md
│   └── 附图清单.md
├── 附图/
│   ├── 图1-....png
│   └── 图1-....drawio
├── 参考分析/
│   ├── 00-申请前治理记录.md
│   ├── 01-代码能力事实与验证边界.md
│   ├── 02-现有技术检索与独立权利要求对比.md
│   ├── 03-开源项目雷同与公开风险.md
│   ├── 04-代码改造与测试回执.md
│   └── 05-权利要求策略与特征映射.md
├── 申请前校对稿/
│   └── 发明专利申请前校对稿.pdf
└── 99-内部校验/
    ├── provenance.json
    ├── 结构自检.json
    ├── 页面渲染/
    └── 生成与审计脚本/
```

只生成任务需要的子集。完整申请模式才要求全部主要目录。

## 申请前治理记录

每个案件在当前版本内维护一份 `00-申请前治理记录.md`。旧台账、旧申请稿和口头陈述只能帮助定位，不得直接复制成当前结论。身份原件、证照、联系方式和签章材料保存在仓库外的受控位置。

### 公开披露

逐项记录可能影响新颖性的行为：

| 字段 | 要求 |
|---|---|
| 日期时间 | 区分文件修改时间、发送时间和首次可被公众获得的时间 |
| 内容与版本 | 文件、页面、代码提交、演示或截图；记录 SHA-256 |
| 渠道与地址 | 仓库、网站、邮件、网盘、客户演示、投标、培训、展会或社交媒体 |
| 接收对象与权限 | 具体对象、是否不特定公众可得、访问控制和保密约束 |
| 最早证据 | 原文件、提交记录、邮件头、网页存档、服务器日志或权限记录 |
| 当前可访问性 | 当前是否仍可访问；删除页面不改变已经发生的公开事实 |
| 特征映射 | 映射到拟申请独立权利要求的必要技术特征，不只记录标题或产品名称 |
| 结论与缺口 | 已核验、仅用户陈述、无法确认，以及需代理师判断的事项 |

- “用户称未公开”只能记录为带日期和范围的陈述，不能写成已经核验的法律结论。
- 发生疑似公开时，不删除、覆盖或回填历史证据；先保存原始载体、时间、访问权限和哈希，再停止进一步公开。
- 普通产品发布、客户演示或互联网公开不得自行假定适用六个月例外。

### 权属、贡献与版本冻结

| 字段 | 要求 |
|---|---|
| 申请主体 | 名称、主体类型和确认状态；证照信息不写入仓库 |
| 发明人贡献 | 每名自然人对应到具体技术特征、关键选择或实质性改进 |
| 权属依据 | 职务成果、委托、合作、转让或其他依据及待补证明 |
| 冲突核查 | 是否在其他主体、项目、仓库或申请中主张同一成果 |
| 代码基线 | 根目录、`origin`、分支、提交标识、提交时间和工作树状态 |
| 关键证据 | 实现、测试、事实账本和构建脚本的当前 SHA-256 |
| 对外发送 | 文件名、版本、哈希、接收人、时间、渠道和保密约束 |

- 职位、投资、管理、提示词输入或使用 AI 工具本身不能替代自然人的创造性贡献事实。
- 工作树存在未提交修改时，`HEAD` 不能单独称为完整实现基线；应同时冻结当前文件哈希，或先形成经确认的提交。
- 排除令牌、证书、客户数据、运行状态、第三方依赖、构建缓存和无关源代码。
- 未确认的申请人、发明人、联系人、地址和日期保持空白，并在交付报告中列为缺口。

## 唯一权威

- 事实账本控制技术真相。
- `申请文件/` 中的规范源控制申请文字。
- `附图/` 中最终 PNG 和可编辑源共同控制图形。
- DOCX、PDF、页面渲染和 XML 准备文件均为派生产物。

发现派生产物与规范源不一致时，修正规范源后重新生成，不直接在派生产物中形成第二套内容。

## 来源清单

在 `provenance.json` 中为每个来源分配唯一角色并记录当前 SHA-256：

- 工作空间与版本；
- 事实账本和实现代码；
- 测试回执；
- 现有技术及公开链接；
- 规范摘要、权利要求、说明书和附图；
- 模板和版式合同；
- 文档构建、PDF 导出和审计脚本；
- 最终 DOCX、PDF 和绘图页。

同一路径不能同时作为本发明事实源、现有技术和版式权威。原始公开专利不得进入本发明规范源、代码证据或身份角色。

### `provenance.json` 最小结构

完整申请包使用下面的角色结构。除 `workspace_root` 可为绝对路径外，所有相对文件路径均以案件版本目录为基准，而不是以 `provenance.json` 所在目录为基准：

```json
{
  "artifact_type": "review_pdf",
  "workspace_root": "所属项目根目录",
  "invention_topic": "发明名称",
  "review_label": "申请前校对稿（非电子提交格式）",
  "output_pdf": "申请前校对稿/发明专利申请前校对稿.pdf",
  "canonical_application_sources": {
    "abstract": "申请文件/说明书摘要.md",
    "claims": "申请文件/权利要求书.md",
    "description": "申请文件/说明书.md",
    "drawings": ["附图/图1.png"],
    "abstract_figure": "附图/图1.png"
  },
  "implementation_evidence": ["项目内源代码路径或绝对路径"],
  "layout_authority": "Skill 内 review-pdf-format.md 的绝对路径",
  "official_rule_authorities": ["当前 CNIPA 官方 HTTPS 地址"],
  "build_pipeline": {
    "document_builders": [],
    "pdf_exporters": [],
    "orchestrators": []
  },
  "disclosure_materials": ["技术交底书/技术交底书.docx"],
  "raw_publication_references": [],
  "source_hashes": {"每个已分配来源路径": "sha256"},
  "confirmed_identity": {"applicant": "", "inventors": []}
}
```

- `canonical_application_sources` 只指向本申请规范源，不能指向交底书、参考专利或 PDF 派生文件。
- `artifact_type` 只使用 `review_pdf`、`application_sources`、`xml_preparation`、`analysis_bundle` 或 `section_bundle`；`xml_preparation` 只表示提交准备，不表示 XML 通过官方校验。
- `raw_publication_references` 只记录用于检索的公开文献；不得与规范源、代码、构建脚本或附图复用同一路径。
- 未确认身份允许为空，但构建器和 PDF 都不得自行补齐。
- `source_hashes` 必须覆盖规范源、实现证据、版式合同和实际使用的构建脚本；多余、缺失或不一致均失败。
- `official_rule_authorities` 只接受当前 `https://*.cnipa.gov.cn/` 官方来源；提交前重新联网核验。

## SHA-256 清单

`02-文件校验.sha256` 至少包含主 DOCX、规范申请源、PNG、可编辑附图、参考分析、校对 PDF、`00` 和 `01`。不要把清单自身写入清单。

冻结后重新计算并逐项验证。任何主文件发生变化，都要重建清单和受影响的派生产物。

## 审计配置

`scripts/audit_delivery_bundle.py` 默认使用 `full` 配置并采取失败关闭：空目录、缺少根文件、缺少哈希清单、缺少 `provenance.json`、PDF 无法解析或来源冲突均失败。

- `--profile full`：完整申请准备包；必须提供来源记录和规范申请源。
- `--profile analysis`：仅事实、查新或策略分析包；仍要求可验证的清单和至少一个实质文件。
- `--profile section`：单章节或小范围修订包；仍要求可验证的清单和至少一个实质文件。
- `--allow-partial`：只把缺少标准根文件或分析/章节来源记录降为警告；不会放宽空包、损坏文件、越界路径、哈希错误、隐私元数据、外部关系或 Git 隔离失败。

不要使用 `--allow-partial` 让完整申请包“通过”。任何 XML 仅做文件存在性和来源记录审计；是否符合当期电子提交标准必须由官方工具和系统回执证明。

## 保密和 Git

把模板、交底书、申请稿、附图、查新分析、代码证据、身份、QA 页面和生成脚本视为未公开申请材料。

- 保存在用户授权的项目内私有或忽略目录；
- 未经单独授权，不提交、推送、上传或发给外部服务；
- 交付前分别检查 tracked、staged 和未忽略文件；
- 不把其他项目的材料复制进当前案件；
- 不把秘密、运行数据或无关源代码附在代理交付包中。

## 迭代记录

版本记录只写：

- 版本时间和基准；
- 修改原因；
- 事实来源变化；
- 是否影响查新；
- 是否影响权利要求；
- 旧版和原模板哈希是否保持。

不强制保存完整对话，不把版本记录写入正式申请正文。

## 完成交付报告

说明：

- 实际生成的主文件；
- 代码和测试基线；
- 查新截止日与范围；
- 授权稳健优先或保护范围优先策略及选择依据；
- 未确认和未验证项目；
- DOCX/PDF 页数和逐页检查结果；
- 哈希核验和 Git 隔离结果；
- 校对 PDF 不是当期电子提交文件；`xml_preparation` 也不等于 XML 已通过官方校验。
