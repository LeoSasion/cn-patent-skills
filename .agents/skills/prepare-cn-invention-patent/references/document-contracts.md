# 技术交底书与正式申请文本合同

## 产物边界

| 产物 | 控制内容 | 不得控制 |
|---|---|---|
| 事实账本 | 当前实现、测试和验证边界 | 法律格式、官方字段 |
| 查新与特征矩阵 | 有限检索范围内的现有技术比较 | 发明人身份、申请结论 |
| 技术交底书 | 代理师理解技术所需的事实、步骤和替代方式 | 正式申请顺序、PDF封面、官方元数据 |
| 规范申请源 | 题目、摘要、权利要求、说明书和附图的一致文本 | 未确认申请信息、授权状态 |
| 申请前校对 PDF | 规范申请源的版式和视觉校对 | 当期电子申请文件身份 |

每个来源只承担一个主要角色。参考专利只能提供经核验的现有技术内容或抽象写作规则，不能提供本发明事实。

## 技术交底书

### 模板优先级

1. 用户提供的 DOCX 控制字段、问题顺序、表格、页眉页脚、页面几何和样式。
2. 无用户模板时，复制 `assets/技术交底书_空白模板.docx` 后填写。
3. 原模板保持字节不变；用户明确要求原位修改时，先创建字节级备份。

不要用外部 Skill 的自由 Markdown 六章模板覆盖用户的八部分表格。不要把模板里的示例、蓝色标题、“实用新型”提示或注意事项复制到正式申请。

内置模板使用命名内容控件，不使用段落或表格索引。先运行 `scripts/check_template_hash.py`，再用 `scripts/fill_disclosure_template.py` 写入副本；标签、哈希或页面几何不匹配时停止。用户模板没有内容控件时，应先盘点并基于可见标签定位，不靠固定索引猜测。

### 字段规则

- 只填写已确认或可追溯的事实。
- 未确认的联系人、电话、传真、邮箱、申请人、发明人、地址和日期保持空白。
- 最终 DOCX 中不要用 `[待填写]` 代替未知字段。内置空白模板的灰色提示仅用于未填写状态；生成交付副本时应清空未知身份字段。
- 不把发明人自动当成联系人。
- 不编造最接近专利号、公开日、新颖性或创造性结论。

### 八部分内容

1. **技术问题**：只写实际方案能够防止的技术失败。
2. **背景与最接近方案**：说明现有流程及其局限；完整查新矩阵另附。
3. **缺点与目的**：每个缺点对应一个具体目的。
4. **详细方案**：定义对象和前提；给出有序步骤、异常分支、系统模块及输入、输出、状态和交互；逐图解释。
5. **关键点和保护点**：先写核心组合，再写从属细化和保护对象形式。
6. **优点**：说明技术手段为何产生该效果，不写营销口号。
7. **替代方案**：列出保持核心关系不变的算法、存储、部署、步骤或容错替代。
8. **辅助资料**：列出版本边界、代码、测试、附图、检索和未决信息，不写官方申请编号。

用简洁、通俗的中国本土化术语。英文缩写首次出现时给出中文全称；一个对象只用一个中文主称谓。

## 正式申请规范源

### 唯一内容源

在 `申请文件/` 维护：

- `题目.md`
- `说明书摘要.md`
- `权利要求书.md`
- `说明书.md`
- `附图清单.md`

申请前校对 PDF、DOCX 或 XML 准备文件均从这些规范源派生，不在派生产物中独立修改技术内容。

### 撰写顺序

1. 冻结核心创新链和权利要求骨架。
2. 写权利要求书。
3. 收敛题目。
4. 写说明书摘要。
5. 写背景技术。
6. 写发明内容和有益效果。
7. 写附图说明和具体实施方式。
8. 做全文、附图和代码映射审计。

### 各部分规则

**题目**

- 体现核心技术对象和必要技术特征，不写宣传语。
- 保护对象与后续权利要求一致。

**摘要**

- 写公开内容、核心步骤和技术效果，不逐句复制权利要求。
- 按当期 CNIPA 校验规则控制长度；未重新核验时默认不超过 300 字。
- 有说明书附图时，从现有附图中选择最能反映主要技术特征的一幅作为摘要附图。

**背景技术**

- 只写现有技术及具体缺陷，不提前写本发明方案。
- 以检索矩阵支持最接近方案，不堆砌行业趋势或政策。

**发明内容**

- 以权利要求为骨架，补充技术原理和必要关系。
- 每项有益效果写清楚“技术手段—工作机制—产生的效果”。
- 不写未经验证的定量指标。

**权利要求书**

- 使用 `references/search-and-claims.md` 的目标策略。
- 主权项覆盖核心区别组合；从属权逐层收窄。
- 不机械堆叠方法、系统、设备、介质和程序产品。

**具体实施方式**

- 先总述，再按步骤或模块逐项展开。
- 说明输入、输出、状态、约束、失败分支和替代实现。
- 每幅图至少在正文中有一次明确引用。
- 公式、变量和数值例子必须来自当前事实，并与权利要求一致。

## 语言纪律

- 只写必要重点，但完整公开核心关系和失败路径。
- 优先短句和明确主语，避免“赋能、智能化、高效”等空泛词。
- 不把产品功能列表当成技术方案。
- 不把散列值、标识或版本号本身写成创新效果。
- 不出现 Skill 名、脚本名、内部自检清单或流水线痕迹。

## 统稿检查

- 题目、摘要、权利要求和说明书保护对象一致；
- 术语唯一；
- 背景缺陷、目的、方案和效果逐项对应；
- 权利要求在说明书和附图中有支持；
- 说明书没有比事实账本更多的能力；
- 每张图的图号、名称、引用和可编辑源一致；
- 申请人和官方字段没有被猜测补齐。
