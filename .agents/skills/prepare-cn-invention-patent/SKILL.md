# 中国发明专利申请准备

## 目标与边界

围绕一个发明主题建立可追溯的申请准备链：

`当前实现与测试 → 事实账本 → 现有技术与开源对比 → 申请策略 → 权利要求骨架 → 技术交底书 → 规范申请源 → 附图 → 申请前校对稿 → 交付审计`

技术交底书、规范申请源和校对 PDF 是不同产物。前一产物可提供事实线索，但不自动控制后一产物的法律结构、版式或官方字段。

本 Skill 提供申请准备与质量控制，不构成法律意见，不代理正式提交，也不保证授权。申请人、发明人、权属、公开披露、优先权、提交策略和最终申请文本应由用户与具备相应资质的专利代理师或律师确认。

## 路由

先识别任务，只执行所需路径：

1. **完整申请准备**：执行全部主流程。
2. **事实、查新或可专利性初步分析**：执行相应门禁，只交付限定范围的分析。
3. **填写技术交底书**：先完成事实门禁；外部检索未完成时把它列为缺口，不把交底书当作申请定稿。
4. **撰写或修改单一章节**：读取事实账本和规范源，只修改目标章节，再检查受影响内容。
5. **已有稿迭代**：按改动影响重跑事实、检索或权利要求门禁，创建新版本，不默认覆盖旧稿。
6. **明确从头重做**：旧稿退出技术事实来源，仅保留为版本证据。
7. **电子提交准备**：核验当期 CNIPA 规则、工具和数据标准；没有真实转换与验证能力时停在准备阶段，不自造或冒充可提交 XML。

解读一件已经公开或授权的专利不属于本 Skill；改用 `$explain-cn-patent`。

## 不可跳过的原则

- 默认只处理中国发明专利；改变类型前先确认适用流程。
- 当前代码、机器合同和实际测试优先于产品说明、旧交底书和旧申请稿。
- 模拟数据只能证明测试场景，不能冒充生产事实、客户效果或经营数据。
- 未确认的申请人、发明人、联系人、地址、电话、邮箱、日期、优先权和官方编号保持空白。
- 不从公司名称推断申请人，不从管理关系或工具使用推断发明人，不从参考专利复制身份或技术内容。
- 不承诺“没有重复”“一定授权”或“不会无效”；结论必须绑定检索日、文献集和证据范围。
- 未经用户明确要求，不为配合既定文案修改代码；用户已授权改造时，先实现并测试，再冻结新的事实基线。
- 未经用户单独授权，不提交、上传、公开、提交 Git 或调用专利申请系统。
- 原始材料和旧版本保持不变；实质修订进入新版本目录。

## 主流程

### 0. 确认范围、保密和策略

1. 核对项目根目录、分支、`origin`、发明主题和交付范围。
2. 仓库存在 `.codegraph/` 时，先用 CodeGraph 理解入口、符号和调用链。
3. 按 `references/delivery-contract.md` 复核公开披露、权属贡献、身份确认、版本基线和 Git 隔离；旧台账只作线索。
4. 创建独立版本目录，保持旧版和原模板只读。
5. 并列说明“授权稳健优先”和“保护范围优先”的主要取舍，记录用户选择。用户尚未选择且差异会改变独立权利要求时，先交付比较，不静默采用任何一方。

### 1. 建立事实账本

读取 `references/evidence-gate.md`。每项核心特征标明实现位置、调用关系、测试、证据性质、已实现程度、异常边界和可进入的写作层级。

核心技术链证据不足时不用语言补齐。若用户授权代码改造，先完成实现、负向与恢复测试，再重新生成事实账本。

### 2. 检索并比较现有技术

读取 `references/search-and-claims.md`。先用题目和摘要筛选，再阅读最接近文献的独立权利要求及必要说明书段落；同时比较公开日期更早的开源项目、论文和产品实现。

分别判断单篇覆盖、组合覆盖及结合动机、术语相似但技术关系不同，以及申请日前自有公开披露。不得用标题或关键词差异代替独立权利要求比较。

### 3. 冻结创新链与申请策略

用一句话写出不可拆散的核心区别组合，删除单独存在时不具区分力的通用能力。

- **授权稳健优先**：把已有证据和检索支持的必要区别组合写入主独立权利要求，保留逐层收窄的回退位置。
- **保护范围优先**：采用较概括的主权项和多层从属回退，同时保留区别于最接近现有技术的必要关系。

两条策略都不得超出事实账本。权利要求数量和编号本身不提高授权可能性。

### 4. 先定权利要求骨架

按 `references/search-and-claims.md` 形成一项主独立权利要求和逐层收窄的从属权利要求；只有事实充分且确有必要时，增加对应系统、设备或介质权利要求。

逐特征映射到实现、测试、说明书段落和附图。映射不完整时先补说明或删减特征，不反向编造实施方式。

### 5. 生成技术交底书

读取 `references/document-contracts.md`。

- 用户提供 DOCX 时，以其字段和版式为准，先盘点内容控件、样式、修订、元数据和外部关系。
- 无用户模板时使用 `assets/技术交底书_空白模板.docx`，先读取 `references/bundled-template-contract.md` 并运行 `scripts/check_template_hash.py`。
- 内置模板通过稳定内容控件标签填写，不按段落或表格索引猜测；使用 `scripts/fill_disclosure_template.py` 在副本上生成。
- 未知身份字段保持真正空白；查新矩阵、代码证据和内部自检不写进交底书正文。

使用 documents Skill 创建或编辑 DOCX，完成后渲染全部页面并逐页检查。

### 6. 生成规范申请源

继续按 `references/document-contracts.md`，以已确认的权利要求骨架为中心完成题目、说明书摘要、背景技术、发明内容、附图说明（如有附图）、具体实施方式和全文统稿。

交底书只用于事实交叉核对。规范申请源必须再次对照当前代码、事实账本和检索矩阵；不得把模板提示、联系方式或不相关专利类型带入正文。

### 7. 生成和复核附图

读取 `references/figures-and-validation.md`。附图以代码事实为准，使用中文、黑白线条和必要标号。交付 PNG 与可编辑源文件；每幅图都在说明书中引用和解释。

正常主流程、条件分支、异常恢复和限制说明分别表达。禁止错误串行关系、无连接点穿线和只修改导出图不修改源图。

### 8. 生成申请前校对稿

读取 `references/filing-boundary.md`、`references/review-pdf-format.md` 和 `references/figures-and-validation.md`。

只从规范申请源生成 PDF，并在首页精确标注 `申请前校对稿（非电子提交格式）`。校对稿用于申请人与专业代理人员审阅，不是电子提交文件。

使用 PDF Skill 渲染并检查全部页面。Windows 环境缺少 LibreOffice 且 Microsoft Word 可用时，可用 `scripts/render_with_word.ps1` 只读导出 PDF；不得把 Word 自动保存回原 DOCX。

### 9. 冻结和审计

按 `references/delivery-contract.md` 生成交付清单、来源清单、SHA-256 和内部审计材料。完整申请包运行：

```powershell
python scripts/audit_delivery_bundle.py --root "<版本目录>" --repo "<项目根目录>" --provenance "<版本目录>/99-内部校验/provenance.json" --require-git-isolated
```

分析或章节包只有在用户明确接受部分交付时才加 `--profile analysis` 或 `--profile section`；缺失标准根文件时还必须显式加 `--allow-partial`。该选项只放宽包结构，不放宽损坏文件、越界路径、隐私元数据或来源冲突。

只有内容、页面、哈希、来源和所选 Git 隔离要求均通过后才交付。明确列出仍为空的字段、未验证边界、检索范围和 PDF/XML 边界。

## 迭代与停止条件

- 错字或排版：重做文档与页面检查。
- 术语、图号或流程关系：检查全文和全部附图。
- 新模块、新步骤或实现变化：重做事实账本和相关测试。
- 核心区别或保护方向变化：补充检索并重做权利要求骨架。
- 用户要求不参考旧稿：从当前实现重新取证，旧稿不参与术语、流程或保护点选择。

停止扩大文本并明确缺口，如果核心能力只有文档声明、异常主张没有相称测试、最接近现有技术已覆盖核心组合、主题混入不具单一性的方案、身份或权属未确认，或请求可直接提交的 XML 但缺少当期官方工具和真实验证回执。
